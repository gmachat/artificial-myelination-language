# Benchmarking AML

AML's central claim is lower total token cost for producing correct software.
That claim must be measured in layers rather than inferred from short syntax.

## Built-in source benchmark

Run:

```sh
aml benchmark
aml benchmark --json
```

The corpus contains paired AML, Python, and JavaScript programs with equivalent
validation, contracts, output, and entrypoint behavior. Select one comparison
or run both:

```sh
aml benchmark --language python
aml benchmark --language javascript
aml benchmark --language ruby
aml benchmark --language go
```

The command measures only source an author or coding agent must produce. It
does not count code generated by the AML compiler because that is deterministic
tool output, not model output.

When the optional `tiktoken` package is installed, the benchmark uses the
`cl100k_base` tokenizer. Otherwise it reports `lexical_estimate`, a transparent
approximation that must not be presented as an exact model-token count.

Install exact token counting with:

```sh
python3 -m pip install "artificial-myelination-language[benchmark]"
```

## What the built-in benchmark does not prove

Shorter authored source does not establish lower total AI cost. A complete
evaluation must record, for each identical task and model:

- task prompt tokens;
- AML or comparison-language reference material supplied to the model;
- reasoning tokens where the model API exposes them;
- generated source tokens;
- compiler and test diagnostics returned to the model;
- repair-round tokens;
- first-pass and final correctness;
- human review time.

AML should be considered token-efficient only when its complete workflow beats
the comparison language across a representative task corpus.

The compact reference is also regression-tested at no more than 500 lexical
estimate tokens. This prevents language growth from silently erasing authored
source savings with a larger agent prompt. It is a budget guard, not proof of
lower total tokens.

## Fair-comparison rules

1. Require equivalent behavior, validation, and failure handling.
2. Use the same model, sampling settings, task prompt, and test suite.
3. Include AML documentation in AML prompt costs.
4. Count failed attempts and repair conversations.
5. Publish the task corpus and raw measurements.
6. Separate authored source from deterministic compiler output.

## End-to-end AI workflow benchmark

The reproducible harness in `benchmarks/ai_workflow` measures the complete
initial-generation and repair loop against TypeScript. It uses a provider-neutral
adapter protocol rather than embedding credentials or depending on one model API.

```sh
node benchmarks/ai_workflow/benchmark.mjs run \
  --adapter /absolute/path/to/adapter \
  --run-dir benchmarks/ai_workflow/runs/trial-1 \
  --task inventory
```

Every adapter response records provider-reported input, output, and reasoning
tokens. The harness retains failed attempts, sends evaluator feedback into the
next repair, and totals all rounds. A savings percentage is withheld unless both
conditions use the same model and pass the same evaluation level.

The versioned catalog currently contains ten full-stack tasks. Run every task
and aggregate tokens, pass rates, first-pass success, and repair rounds with:

```sh
node benchmarks/ai_workflow/benchmark.mjs suite \
  --adapter /absolute/path/to/adapter \
  --run-dir benchmarks/ai_workflow/runs/suite-1 \
  --repetitions 3
```

This command makes at least 60 model calls before repairs. Use `--tasks` with a
comma-separated subset for development trials. A suite-level saving is emitted
only if every scheduled comparison is eligible; failed tasks are never silently
removed from the aggregate.

The default structural evaluator compiles and generates the AML application and
checks equivalent authored TypeScript project requirements. An opt-in runtime
level runs both applications against identical black-box API, validation,
persistence, deletion, and browser-serving tests:

```sh
node benchmarks/ai_workflow/benchmark.mjs run \
  --adapter /absolute/path/to/adapter \
  --run-dir benchmarks/ai_workflow/runs/runtime-trial-1 \
  --execute --engine docker
```

Docker and Podman are supported. Runtime evaluation sanitizes the dependency
manifest, disables package lifecycle scripts, and executes generated code with
network access disabled plus container capability and resource limits. Package
download is necessarily a separate network-enabled step. Savings are compared
only when both conditions pass the same structural or runtime level.

The initial catalog deliberately stays within AML's implemented full-stack
profile so both conditions can receive identical behavioral grading. Future
catalog versions should add separate CLI, data-processing, authentication, and
API-only cohorts only after AML has equivalent primitives and evaluators.
